## Resumen y cronología

Tres contraseñas incorrectas en una conexión SSH fueron seguidas de un acceso correcto en una conexión nueva. Wazuh generó `100100` y conservó los tres fallos en `previous_output`.

| Hora del mensaje original | Evento |
| --- | --- |
| 12:12:40 | Primer fallo, PID 2232, puerto 33978 |
| 12:12:43 | Segundo fallo, mismo PID y puerto |
| 12:12:49 | Tercer fallo, mismo PID y puerto |
| 12:13:03 | Éxito, PID 2234, puerto 57914 |

Todas las líneas pertenecen al 22/10/2026, al mismo origen y usuario. El intervalo entre primer fallo y éxito es 23 segundos. Antes del caso 003 se corrigió la hora de las tres VMs a Europe/Madrid con NTP. El dashboard muestra las 14:13; la tabla conserva las marcas originales de los mensajes para calcular la duración.

## Comprobaciones realizadas

- Regla probada antes del reinicio con `wazuh-logtest`: positiva, dos fallos, otro usuario, otra IP, éxito aislado y control temporal.
- Fallos sin éxito observados como prefijo de la prueba positiva, sin alerta propia.
- Configuración validada con `wazuh-analysisd -t`; manager activo tras el reinicio.
- Terminal del cliente con tres solicitudes rechazadas y conexión correcta posterior.
- Alerta real con origen, destino, cuenta, nivel y registros previos coherentes.

## Decisión

Cerrar como simulación autorizada: la detección identifica la secuencia prevista, sin evidencia de acceso no autorizado. No se realizaron bloqueos, deshabilitación de cuenta ni escalado real. No se etiqueta como falso positivo solo por ser una actividad benigna conocida.

## Criterio de escalado en un entorno real

Escalar a N2 si no puede justificarse el acceso, el usuario lo niega, el origen es inesperado o se observa actividad posterior sospechosa. Entregar los registros, la cronología y zona horaria, identidad, privilegios, contexto y límites de visibilidad. La telemetría posterior de comandos y procesos no se ha validado en este caso.
